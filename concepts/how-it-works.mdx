Network Policy Generator is a Kubernetes operator built on [controller-runtime](https://github.com/kubernetes-sigs/controller-runtime). Every moving part — from traffic observation to policy enforcement — is driven by a single `NetworkPolicyGenerator` custom resource that acts as the authoritative control object. Understanding how the reconciler, monitor, collector, and policy engines interact gives you the mental model to tune, debug, and extend the operator confidently.

## The Control Loop at a Glance

The operator follows the standard Kubernetes reconcile pattern: watch → diff → act. When a `NetworkPolicyGenerator` CR is created, updated, or the requeue timer fires, the `NetworkPolicyGeneratorReconciler` wakes up and drives the resource toward its desired state. The reconciler owns a `Generator` (policy builder), a `Validator` (CIDR and cross-field checks), and a `Recorder` (Kubernetes events), all wired together at startup.

```go
type NetworkPolicyGeneratorReconciler struct {
    client.Client
    Scheme    *runtime.Scheme
    Generator *policy.Generator
    Validator *policy.Validator
    Recorder  record.EventRecorder
}
```

  <Card title="Reconciler" icon="arrows-rotate">

  <Card title="Monitor" icon="eye">

  <Card title="Collector" icon="database">

  <Card title="PolicyEngine" icon="gears">

  </Card>

## Reconcile Walk-Through

<Steps>
  ### Fetch the CR
  The reconciler calls `r.Get` for the `NetworkPolicyGenerator` identified by the request's namespaced name. A `NotFound` error means the resource has already been fully deleted — the function returns cleanly.

  ### Sync phase with mode
  `syncPhase` maps `spec.mode` (`learning` / `enforcing`) to the corresponding `status.phase` (`Learning` / `Enforcing`) and persists the status subresource. If the phase changed, a `PhaseChanged` event is emitted.

  ### Handle deletion
  If `metadata.deletionTimestamp` is set, the reconciler enters the deletion path (described below) and returns immediately, bypassing the normal mode dispatch.

  ### Ensure finalizer
  On the first reconcile after creation, the reconciler adds the `security.policy.io/finalizer` finalizer via `controllerutil.AddFinalizer`. This prevents the API server from garbage-collecting the CR until all generated policies have been cleaned up.

  ### Dispatch to mode handler
  Depending on `spec.mode`, the reconciler calls either `handleLearningMode` or `handleEnforcingMode`. Each handler returns a `ctrl.Result` that tells controller-runtime when to requeue.

  ### Record metrics
  Reconcile duration is observed in a Prometheus histogram (`ReconcileDuration`) and a counter increments for `success` or `error` outcomes.
</Steps>

## Learning Phase: Monitor and Collector

During learning mode the operator does not write any network policies. Instead it records what traffic patterns exist so it can build accurate policy suggestions.

The `Monitor` struct owns a `Collector` and runs a periodic loop:

```go
func (m *Monitor) monitorTraffic(ctx context.Context) {
    ticker := time.NewTicker(m.collectInterval) // default: 30s
    defer ticker.Stop()
    for {
        select {
        case <-ctx.Done():
            return
        case <-m.stopCh:
            return
        case <-ticker.C:
            m.collectTrafficData(ctx)
        }
    }
}
```

On each tick the `Collector` does two things for every pod in the namespace:

1. **Container ports** — Each `containerPort` in the pod spec becomes a `TrafficFlow` with the pod as source, the declared protocol, and the port number.
2. **Environment variable analysis** — Any env var whose lowercased name contains `host`, `url`, or `endpoint` is parsed. The value is split on `:` to extract a hostname and port (defaulting to port 80 if no port is present). Kubernetes in-cluster DNS names (`<service>.<namespace>.svc.cluster.local`) are decomposed to derive the destination namespace and service name. All env-var-derived flows use the `TCP` protocol.

```go
if strings.Contains(strings.ToLower(env.Name), "host") ||
   strings.Contains(strings.ToLower(env.Name), "url")  ||
   strings.Contains(strings.ToLower(env.Name), "endpoint") {
    host, port := ParseHostAndPort(env.Value)
    // build TrafficFlow from host components ...
}
```

<Note>
  The `Monitor` deduplicates flows before storing them. A flow is considered identical when all six fields match: `sourceNamespace`, `sourcePod`, `destNamespace`, `destPod`, `protocol`, and `port`. This prevents the in-memory slice from growing unbounded during a long learning window.
</Note>

## Enforcing Phase: Policy Engine Dispatch

Once the reconciler enters `handleEnforcingMode`, the workflow is:

1. If `spec.templateName` is set, the named template merges its defaults into `spec` (user-defined rules always win).
2. `policy.NewPolicyEngine(spec.policyEngine)` returns a `PolicyEngine` implementation — `KubernetesEngine` by default.
3. `engine.GeneratePolicies(generator)` returns a `[]runtime.Object` slice.
4. Each object is applied via `applyPolicyWithDiff`, which issues a **Create** or **Update** against the API server and reports back the action string (`"Created"` / `"Updated"` / `"Unchanged"`).
5. The diff entries are written to `status.policyDiff` and the count to `status.appliedPoliciesCount`.

The `PolicyEngine` interface is intentionally minimal:

```go
type PolicyEngine interface {
    GeneratePolicies(generator *securityv1.NetworkPolicyGenerator) ([]runtime.Object, error)
    EngineName() string
}
```

Adding a new CNI engine only requires implementing these two methods and registering the engine name in `NewPolicyEngine`.

## Owner References and Garbage Collection

Every generated network policy — whether a Kubernetes `NetworkPolicy`, a `CiliumNetworkPolicy`, or a Calico `NetworkPolicy` — is stamped with an owner reference pointing back to the `NetworkPolicyGenerator` CR that produced it:

```go
OwnerReferences: []metav1.OwnerReference{
    {
        APIVersion: generator.APIVersion,
        Kind:       generator.Kind,
        Name:       generator.Name,
        UID:        generator.UID,
        Controller: ptr.To(true),
    },
},
```

<Note>
  Owner references work for same-namespace objects managed by the Kubernetes garbage collector. For Cilium and Calico custom resources the operator also handles explicit deletion during finalizer processing, because cross-group CRDs may not be covered by the standard GC in all cluster configurations.
</Note>

## Finalizer and Graceful Deletion

The finalizer `security.policy.io/finalizer` is the safety net that guarantees no orphaned policies remain after a `NetworkPolicyGenerator` is deleted.

When `kubectl delete networkpolicygenerator <name>` is called:

1. The API server sets `metadata.deletionTimestamp` and blocks actual deletion.
2. On the next reconcile, the controller detects `!generator.DeletionTimestamp.IsZero()` and calls `handleDeletion`.
3. `deleteNetworkPolicies` iterates over every namespace that received a policy and deletes the corresponding resource by name (`<generator-name>-generated`), tolerating `NotFound` errors gracefully.
4. The finalizer is removed with `controllerutil.RemoveFinalizer` and the CR is updated.
5. The API server now allows the CR to be permanently deleted.

A `PoliciesDeleted` event is emitted and the `PolicyOperations{Deleted}` Prometheus counter is incremented to make the cleanup observable.

## CEL Validation

The CRD ships with server-side CEL validation rules enforced directly by the API server — no webhook round-trip is needed for these invariants:

| Rule | Behavior |
|------|----------|
| `spec.mode == 'learning'` requires `spec.duration > 0s` | Rejected at admission |
| A namespace cannot appear in both `allowedNamespaces` and `deniedNamespaces` | Rejected at admission |
| Exactly one of `port` or `namedPort` must be set on each `GlobalRule` | Rejected at admission |

These rules are defined directly on the CRD types using `+kubebuilder:validation:XValidation` markers and are enforced by any Kubernetes cluster at v1.25 or later.
